StockV 效能優化紀錄

主題：遊戲模式與 YouTube 同時開啟時卡頓（GPU 滿載）的原因、修改與日後可再優化的方向

測試環境：Windows、Chrome 157、Intel UHD Graphics 770 內顯、視窗 1600×900

問題與原因量測方法量測發現修改內容 實測結果載入變慢的修正哪些動畫被取消調整參數未來可再優化踩過的坑

1. 問題與原因

只開遊戲模式（#stage.region-game），旁邊另一個視窗播 YouTube 影像就會卡；YouTube 在背景只聽聲音、或用手機看就不卡。

結論：是 GPU 的問題。Chrome 所有視窗共用同一個 GPU 行程。地圖把 GPU 塞滿後，YouTube 的畫面排不到 GPU，所以卡。 背景播放不用畫影像、手機只有單一畫面，所以不受影響。

真正的瓶頸不是北極光、雲、煙火、烏雲、藍眼淚這些 canvas 特效（它們早就有節流與降解析度），而是地圖上約 100 張 SVG 小圖示（動物、地標、船）。

2. 量測方法

腳本：.tmp_work/perf.mjs（用 Chrome DevTools Protocol 開 headless Chrome，錄製 4 秒追蹤，計算各執行緒的忙碌時間）。

cd .tmp_work
# 先確認 python scripts/serve_local.py 在 8000 埠
node perf.mjs "標籤=要執行的 JS"            # 預設視窗無焦點（模擬在看 YouTube）
FOCUS=1 node perf.mjs "focus=window.dispatchEvent(new Event('focus'))"   # 模擬有焦點
SETTLE=4000 node perf.mjs ...              # 執行 JS 後等幾 ms 再量
SHOT=1 ...                                 # 另存截圖 shot_標籤.png
GPUTOP=1 ...                               # 列出 GPU 行程各事件耗時
PRINT="JS 運算式" node perf.mjs            # 只印出一個值，不量測

看這幾個數字：

  • CrGpuMain busy ms/s：GPU 每秒忙碌毫秒數，1000 代表滿載。這是最重要的指標。
  • GPU ms/commit：每次提交畫面平均要多少 GPU 時間。
  • CrRendererMain：主執行緒（JS、版面、繪製）忙碌時間。

做法是「逐一把圖層 display:none 再量一次」，看 GPU 掉多少，就知道哪一層最貴。

3. 量測發現（修改前，視窗無焦點）

關掉的東西GPU busy（ms/s）判讀
（基準）約 980–1000，每次 60–160msGPU 滿載
#clouds / #aurora / #wfx / #fx 全關約 960特效 canvas 幾乎沒影響
國界 g.world約 970單獨關掉沒差
g.folk-layer（原住民小人）約 850影響小
g.geo-layer（地緣動畫）約 975影響小
g.decor（動物 / 地標 SVG 圖）約 240主因
整個 #map約 15確認問題都在 SVG 內
  • 畫面上約 100 張 <image>，其中 59 張含 SMIL 動畫、共 218 段動畫。
  • 外部 SVG 當 <image> 載入時，裡面的 SMIL 會跟螢幕更新率播放（60 / 144Hz），程式的 loopFps 管不到。
  • 向量 SVG 圖所在的圖塊只要被弄髒（旁邊動物走一步），GPU 就要整張重新光柵化。
  • 圖塊光柵化很貴：把 SVG 預先轉成點陣圖貼上去後，GPU 從 980 掉到約 300–400。
  • CSS 的 filter: drop-shadow 與 url(#soft) 模糊濾鏡在這批圖上的影響很小（單獨關掉看不出差別），但跟點陣圖搭配後還是有些成本，所以順手換掉了影子濾鏡。
  • SMIL 圖檔內沒有任何 <filter>，不用處理。

4. 修改內容

#位置做法目的
1app.js svgInfo / bitmapOf / hrefFor / setAnimHref每張 SVG 解析一次，用 freezeSmil 把動畫固定在 t=0 後，畫到 canvas 存成 PNG Blob URL（解析度 64 / 128 / 256 / 512px，依顯示大小選）向量圖改貼點陣貼圖，GPU 不用重畫
2app.js assignLive / scheduleLive / liveSymbol / setLive / stepLive離畫面中心最近、有動畫的 LIVE_MAX=8 張，把 SVG 內容放進 #map <defs> 的 <symbol>，用 <use> 疊在 <image> 上。pauseAnimations() 停住 SMIL，主迴圈以 LIVE_FPS=15 呼叫 setCurrentTime()保留少量動畫，且幀率可控
3index.html、style.css、buildSvg國界（g.world）移到獨立的 <svg id="borders">，CSS 對 #map、#borders 加 will-change:transform 成為各自合成圖層動物動時不用重畫國界
4app.js loopFps有焦點 60→30fps，無焦點 20→15fps（拖曳 / 縮放不受限）減少每秒提交次數
5app.js stepCssAnims地圖上無限循環的 CSS 動畫（開盤光圈 ping、地標 lmFloat 等）暫停，改由主迴圈推進 currentTimeCSS 動畫原本也是每個 vsync 都在跑
6buildDefs、style.css影子 filter="url(#soft)"（feGaussianBlur）改成放射漸層 #softShadow / #softWake約 100 個影子每幀縮放，濾鏡無法快取
7stepCritters動物夜間 filter 字串值沒變就不寫入（c.nf 快取）避免每幀觸發樣式重算
8app.js assetQ / queueAsset / pumpAssets / assetGateOpen快照製作排進佇列：等地形第一波圖磚畫完才開始、同時最多 4 個、只處理畫面上看得到的圖（離中心近的先）。點陣圖用 CPU 畫布（willReadFrequently）製作，凍結版 SVG 用 data: URL見「載入變慢的修正」：避免拖慢地形載入
9index.html快取版本號 style.css?v=20251114a、app.js?v=20251114h避免讀到舊檔

上表「修改後」是第 6 節的載入修正之後量的。修正前一版是無焦點約 290–390、有焦點約 730–750，差別來自 GPU 畫布的 toBlob 讀回。

保留動畫的圖示數量影響很大：實測 LIVE_MAX=0（全部點陣）時 GPU 約 540，LIVE_MAX=3 約 890，LIVE_MAX=8 約 1000（修改過程中的量測，與上表為不同次執行）。 也就是說有焦點時，保留動畫的圖示越多，GPU 越高。

6. 載入變慢的修正（重新整理後地圖先黑一段）

第一版改完後，重新整理時地形要 5–9 秒才出來（修改前約 2–5 秒），畫面先是一片暗色海洋。

原因（量測得到）

  • 地形圖磚從 IndexedDB 磁碟快取讀取。單獨測試時開資料庫約 20ms、讀 61 張約 5ms；但在頁面載入時，開資料庫要 1.2–1.6 秒、讀取要 3–4 秒。
  • 關掉快照製作後地形約 0.9 秒就畫好；只做 SVG 解析不做點陣圖約 5 秒；全部做約 8 秒。所以是快照製作在跟地形搶資源。
  • 用 CPU profiler 看，canvas.toBlob 本身在主執行緒佔了 3.3 秒：一般 canvas 是 GPU 畫布，toBlob 要把像素從 GPU 讀回來，每次都同步等 GPU。
  • 另外 toBlob 的 PNG 編碼會被排到閒置時間，每次要等約 1 秒，佇列一次只做 2 張時每秒只換好幾張圖。

修正

  • 暫存畫布改用 getContext('2d', { willReadFrequently: true })（CPU 畫布），toBlob 不再卡主執行緒。這是效果最大的一項。
  • 快照製作排進佇列，等地形第一波圖磚畫完（0.4 秒內沒有新圖磚，最多等 8 秒）才開始，同時最多 4 個；等 toBlob 回呼時不佔佇列名額。
  • 只處理畫面上看得到的圖，離畫面中心近的先做；點陣圖工作比解析 SVG 優先。畫面外的圖維持原始 SVG（不在畫面上就不會光柵化）。
  • 凍結版 SVG 改成 data: URL，少建一批 Blob。

結果（重新整理，視窗有焦點，同一台電腦交替量測）

版本地形全部畫好載入期間 long task 合計
優化前（原始版本）約 2.2–6.2 秒（電腦忙碌程度不同）約 0.5–1.9 秒
第一版優化約 5.5–9 秒約 0.7–1.1 秒
修正後約 1.0–1.6 秒約 0.5–0.7 秒

7. 哪些小圖示動畫被取消

專案內共有 201 個含 SMIL 動畫的 SVG 圖檔（assets/critters/、assets/animals/），合計 765 段動畫。 修改後的規則如下，不是固定取消某幾個，而是依畫面動態決定：

情況動畫狀態
視窗有焦點，離畫面中心最近的 8 張（有動畫的圖）保留動畫（每秒 15 格）
其餘所有有動畫的圖取消，改成 t=0 的靜態點陣圖
視窗沒焦點（blur）、動畫開關關閉、系統「減少動態」全部取消（和修改前的行為一致）
沒有 SMIL 的圖（PNG、無動畫 SVG）不受影響
原住民小人（natives.js）、船 / 動物的走動、跳躍、呼吸（JS 驅動）不受影響，仍在播，只是迴圈 60→30fps
雲、北極光、藍眼淚、煙火、烏雲（canvas）不受影響（沿用原本節流）
CSS 動畫（開盤光圈、地標浮動、閃光…）仍在播，改由主迴圈以 30fps 推進

「8 張」是即時排名：拖曳、縮放、切換篩選後 200ms 內重新挑選，被換下來的圖會變回靜態圖，新被選到的才開始動。

動畫內容主要是：旗子 / 水波 / 燈光閃爍（opacity 321 段）、旋轉與位移（transform 222 段）、cx/cy/r 的小圓點移動、火焰 / 煙等。靜態化後這些會停在第 0 秒的樣子。

9. 未來可再優化的方向

  • 有焦點時 GPU 仍有 700+：離上限還有空間。可考慮把靜態圖示合併成一張 sprite atlas 或改畫在一張 canvas 上，不再是上百個獨立 SVG <image>。
  • 動物移動時圖塊仍被弄髒：走動的動物每幀改 transform，可嘗試給每隻動物 will-change:transform 讓它成為獨立圖層，或把會動的動物放到獨立的 canvas。
  • LIVE 動畫改為「滑鼠 hover 才播」或「只在使用者點選的國家附近播」，比距離中心挑 8 張更有意義，也省資源。
  • 給有動畫的 SVG 檔案瘦身：先看上表段數最多的檔案（例如 waitomo-caves.svg 35 段），把裝飾性的閃爍 / 小動畫刪掉或合併。
  • 預先轉成精靈圖（sprite sheet / WebP 動畫）：把少數想保留的動畫離線轉成 N 格點陣動畫，用 canvas 或 CSS steps() 播，完全不跑 SMIL。
  • 讓視窗「沒焦點但仍可見」時主動降級：目前用 blur 判斷；也可考慮用 Page Visibility 加上 IntersectionObserver，在被其他視窗完全遮住時暫停。
  • 提供設定選項：「省電 / 效能模式」直接把 LIVE_MAX 設 0、loopFps 設 15。
  • 地圖平移 / 縮放時（onTransform）重畫整個地形 canvas 與國界，是另一個尚未量測的熱點，可用同樣方法量。

10. 踩過的坑（量測時的注意事項）

  • headless Chrome 預設無焦點：document.hasFocus() 為 false，程式會進入 lowfx 模式（與真實「在看 YouTube」相同）。要量有焦點必須加 FOCUS=1 並手動送 focus 事件。
  • 要用 GPU 模式量：腳本已加 --use-angle=d3d11 --enable-gpu，否則是軟體算圖，結果不準。
  • 量測值會浮動：同一設定多跑幾次取平均；每次改完先等 3–5 秒（SETTLE）讓點陣圖建完。
  • 外部 <image> 裡的 SMIL 無法被暫停：只有內嵌在同一份 SVG 的 SMIL 才能用 pauseAnimations / setCurrentTime，所以才用 <symbol> + <use>。
  • 內嵌後 id 會衝突：每張圖的 id、url(#…)、href="#…" 都要加前綴（lvN-）。
  • 國界移出 #map 後：CSS 選擇器要由 #map .land 改為 #borders .land；shakeEls（地震效果）要把 #borders 一起加進去；tab-hidden 也要隱藏它。
  • 不要用 GPU 畫布做 toBlob / toDataURL：會同步把像素從 GPU 讀回來。要讀像素或編碼的暫存畫布一律加 willReadFrequently: true。
  • 啟動時不要一次丟大量非同步工作：會拖慢 IndexedDB 等其他非同步資源（地形快取）。先讓畫面主要內容出來，再排隊做。
  • 本機伺服器的埠可能被別的程式占用：serve_local.py 會自動換下一個埠。比較新舊版時先用 curl localhost:埠/ | grep app.js 確認版本號。
  • 量測腳本放在 .tmp_work，不屬於網站本體。
